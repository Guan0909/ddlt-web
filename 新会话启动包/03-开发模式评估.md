# 03 · 开发模式评估：分阶段迭代 vs 一次性开发

## 结论：**分阶段提示词迭代开发**（唯一适合本项目的模式）

## 选择依据（针对本项目的四个事实）

1. **存在未验证的外部依赖**：腾讯配额未核额、静态图多色叠加未实测、Canvas 跨域代理未实测。分阶段模式在第 1~2 周就能暴露这些风险；一次性模式会在最后才发现，返工成本最大。
2. **模块间有明确的验收闸口**：引擎（P1）纯逻辑可无依赖先跑通并人工校验时间轴质量 → 数据（P2）回填有量化报告 → 前端（P3）再接真引擎。每个闸口都有可判定标准，适合逐段放行。
3. **上下文经济**：本项目全貌（方案+架构+竞品+品牌+数据）远超单次会话有效上下文。分阶段让每段会话只携带"主上下文 + 当前阶段"，输出质量稳定。
4. **单人项目的纠错半径**：一个人没有 code review，分阶段的"验收清单驱动"是唯一可靠的质量闸门。

## 两种模式对比

| 维度 | 分阶段迭代（推荐） | 单个提示词一次性开发 |
|---|---|---|
| 风险暴露时机 | 第 1~2 周暴露配额/海报链路风险 | 全部风险堆到交付时爆炸 |
| 上下文压力 | 每段轻载，质量稳定 | 超出有效上下文，后半段质量塌缩 |
| 可验证性 | 每阶段有验收清单，可逐项判定 | 只能整体验收，定位问题困难 |
| 返工成本 | 局部返工 | 一处错误牵动全量重新生成 |
| 视觉一致性 | 有原型锚定 + 红线约束，可控 | 长篇生成容易偏离设计 |
| 总耗时 | 约 6 周（与里程碑一致） | 名义上"一次出"，实际调试时间不可控，通常更长 |
| 适用场景 | 多模块、有外部依赖、有质量要求的产品 | 单文件小工具、一次性脚本、纯演示 demo |

## 分阶段的执行顺序与闸口

```
P0 主上下文 → P1 引擎（闸口：成都数据跑出合理时间轴）
           → P2 数据回填（闸口：坐标回填报告 + 抽检）
           → P3 前端主体（闸口：全链路可走通）
           → P4 云函数部署（闸口：配额实测 + 降级演练）
           → P5 海报 Canvas（闸口：低端机实测）
           → P6 AI 文案（可选，闸口：断 Key 全流程无碍）
```

P1 与 P2 互不依赖可并行；P3 依赖 P1；P4 依赖 P1+P2+备案；P5 依赖 P3/P4；P6 永远最后。

## 什么情况下才考虑一次性开发

只有当产品被砍到"单页面 + 无后端 + 无外部 API"（例如纯前端的路线计算器 demo）时才考虑一次性模式——本项目不是。
