# 点定旅途 · 路线规划方案（当前版本）

> 适用代码：`engine/index.js`（浏览器 bundle `web/assets/engine.bundle.js`）、`cloudfunctions/genRoute|reRoute|routePaths`、`cloudfunctions/_shared/routeKit.js`、`web/assets/glmap.js`。
> 原则：**排序永远由算法决定，AI 只写文案**；运行时不调用高德；单条路线腾讯接口调用 ≤15 次。

## 一、输入与输出

| 输入 | 说明 |
|---|---|
| `origin` | 用户搜索选中的完整地点名 + 经纬度（来自腾讯关键字联想，运行时解析） |
| `days` | 1–5 天 |
| `startDate` | 起始日期（周一闭馆处理、文案日期用） |
| `startMin` | 第一天出发时间（05:00–16:00，默认 09:00） |
| `spots` | 城市景点库（60 城、2713 点，含坐标/分类/热度/开放时间/评分/图片/A 级等） |

输出：`{ city, origin, days, dayPlans[], totals, copy, routeId? }`，其中每个 `dayPlans[i].items` 是「通勤/景点/餐食」交错的时间轴，`stats` 为当日站点数、公里、游览/通勤分钟。

## 二、主流程（7 步）

1. **入参校验** `validateInputs`：起点 30km 内要有景点；60km 内可用景点数要够天数；不足报错并给替代建议。
2. **粗筛** `selectCandidates`：市区/远郊分流 → 远郊按 25km 半径打包（单日游览上限 480 分钟）→ 远郊日节数 = `clamp(days-2, 0, 3)` → 市区候选上限 `days × 8`，并限制同分类数量（`MAX_PER_CAT=4`）。
3. **分日** `planDays`：市区候选做 **kmeans 方向聚类**（簇数 = 剩余天数）→ 远郊组各占一天 → **容量再平衡**（单日游览超 cap 时把最低热度点让给最近同类桶）→ **起点命中库内景点时该桶置顶并钉为 D1 第 1 站**（周一闭馆则降级）→ 按热度排序截取前 `days` 个桶，溢出点进 `overflow`（返回给前端提示）。
4. **日内排序** `orderStops`：贪心最近邻（或从 pinned 起）→ **2-opt**（按代价函数）→ `slotFix` 时段软约束（见下）。
5. **时间推演** `runClock`：按顺序逐站排时钟，处理通勤/营业时间/吃饭/收束/回程，排不下或回程太晚的站进 `dropped`。
6. **云端微调** `refineWithRealCommute`（genRoute 云端）：对每天用**真实通勤分钟**再做一次 2-opt（带交叉/折返惩罚、时段组软约束），然后 `retimeDay` 全量重校验时间表。
7. **组装**：`totals` 汇总、AI/模板文案（含每日主题名）、`routeId`（分享链接）。

## 三、日内排序（核心）

- **代价函数** `routeCostOf(order)`：

  `cost = Σ相邻直线距离(m) + 交叉段数 × 600 + 折返次数 × 350`

  其中「交叉」= 两条不相邻线段相交（平面近似），「折返」= 连续两段夹角 cos < −0.82。
  → 600m 相当于「多绕 600 米也不允许一次交叉」，所以路线天然倾向单向环线，不会西→东→西来回穿。
- **2-opt**：反复尝试反转任意子段，cost 下降 ≥5m 才接受；pinned 首站不动；最多 40 轮。
- **时段软约束** `slotFix`：把「早去」点前移、「夜景/演出」点压尾；**只有当重排后代价 ≤ 原代价 ×1.08 才采纳**，否则保留空间更顺的顺序。
  - 「夜景」只在 `cat==='夜景'/'演出'` 或含 `夜游|夜市|看演出|灯光秀` 标签时才强制压尾；湖滨步行街这类只是「商圈」不压尾。
- `pinned`：起点命中库内景点 → 该点固定 D1 第 1 站；无 pinned 时从起点贪心。

## 四、时间推演 runClock

| 规则 | 值 |
|---|---|
| 出发 | `startMin`（默认 09:00；可选 05:00–16:00） |
| 日常收束 | 最后一站游览结束 ≤ 19:30；到家 ≤ 21:00 |
| 远郊日放宽 | 游览 ≤ 20:30；到家 ≤ 21:45 |
| 午餐 | 11:30 起、最晚 13:00 开始，占 60 分钟；13:00 前到「美食」站点则视为含餐 |
| 晚餐 | 17:30 起、最晚 18:30 开始，占 60 分钟 |
| 营业时间 | 未开门则等待；来不及入场则跳过；剩 ≥45 分钟可缩短游览至闭馆 |
| 纯夜场 | 17:00 后开放的夜场（演出等）允许演到散场，不受日常收束限制 |
| 周一闭馆 | `closed_mon` 景点在周一时不排入，进 dropped（原因「周一闭馆」） |
| 回程太晚 | 从末尾撤站重排（最多撤 2 站） |
| 排不下 | 按当前顺序尝试后续站点，最终排不下的进 `dropped`（原因「时间排不下」） |

- 游览时长：库内 `dur`（缺省 90min）；通勤默认估算 `estimateCommute`：直线 ×1.3 后 <1.5km 步行（4.5km/h）、<15km 公交地铁（16km/h×1.2 + 8min 底）、<60km 打车（32km/h）、更远城际（45km/h）。云端用腾讯真实时长替换。
- 单日站数上限 `MAX_STOPS_PER_DAY=8`，实际按可用时间自然收敛；动态容量 `cityVisitCap = max(480, min(720, (19:30 − startMin) − 60))`（起点晚则少排）。

## 五、云端真实通勤再优化（reRoute / refine）

- `reRoute` 入参 `{city, origin, date, startMin?, suburb?, stops:[{id,dur?}]}`：用户拖拽排序/移动天后调用。
- 流程：按显式顺序保留 → 用腾讯真实通勤分钟做 2-opt（`cost = 环线分钟 + 交叉×8min + 折返×4min`，带守卫：只有明显更优才换）→ `retimeDay` 全量重校验（时间窗/餐/收束/回程）。
- 时段组（early/mid/late）只在「更顺空间顺序」不明显绕路时才保留，避免标签导致折返。

## 六、路线绘制（地图）

1. **取几何** `routePaths` 云函数：每条腿调腾讯 direction（步行/驾车；**公交腿改用驾车路网几何**，因为公交 polyline 常是简化直线）→ 解压 polyline → **道格拉斯-普克抽稀**（步行 6m / 公交 8m / 驾车 12m）→ **端头吸附**（≤120m 才接到站点）→ **可信度校验**（绕路系数 <1.02 或偏离直线 < max(20m, 3%) 判为假几何 → 返回 null）→ 路径缓存 7 天（公交当日）。
2. **前端绘制** `glmap.js`：
   - 相邻腿在站点处相接（≤45m）→ **合并为一条连续折线**（模仿主流地图，单层渲染）；
   - 主线 **4–7px 实色、圆角、无白色描边**（宽度随 zoom 分级：<11.5/11.5–13/≥13/≥14.5）；
   - **失败/假几何/坐船相关腿** → 浅灰虚线（不冒充真实道路，避免横穿湖面的假直线）；
   - 端头 120–600m 缺口 → 浅色细虚线衔接（表达「最后一段步行」）；
   - 站点标签带序号（「1. 两江夜游」…），起点用「起」圆点；
   - 视野：规划模式以起点为心 6km 半径（当天都在 6km 内才 fit 全部点，远郊日只显示起点周边）；编辑模式 15km。
3. **缩放**：不再使用「站点直连示意线」概览模式（已删除：它在缩小时会形成横穿湖面的假路），任何缩放级别都只画真实路网。

## 七、不变量与约束

- 路线顺序、时间、通勤由算法生成；AI 只写每日主题与推荐理由文案，不改顺序。
- 运行时禁止调用高德；评分等字段离线入库（`heat`）。
- 单条路线腾讯调用 ≤15 次（direction 按腿缓存、静态图按需）。
- 删除/改名以库为准，任何路线都只用库内景点（用户搜索起点除外）。

## 十、已知待定

- **环线方向偏好**：当前为「最短闭环」（先近后远、终点靠近起点）；若希望「湖滨这类商圈做首站、顺时针推进」，需新增方向偏好规则（该日约 +2~3km）。
- 站点 >8 或跨城串联时可引入 OR-Tools 求解器（当前 greedy+2-opt 在 ≤8 站足够）。

### 补充（2026-10-19）：高德式日内智能排序 + 单线绘制

**排序**（云端 `refineWithRealCommute`）：
1. 用腾讯**距离矩阵**（每模式/每天 1 次调用，全对时长一次拿全）取真实路网分钟；
2. 在真实分钟矩阵上做**精确 TSP（Held-Karp 动态规划，≤8 站，含回程）** → 等价高德「途经点智能排序」；
3. **方向偏好**：起点 3km 内有「商圈/街区」时优先作为首站（最多容忍 +5 分钟通勤）——解决「先西湖再湖滨」的观感问题；
4. 夜游/夜市/演出仍强制靠后（不满足则退回分组顺序）；最后 `retimeDay` 全量重校验。

**绘制**（`glmap.js`）：合并腿时按约 20m 网格跳过已画过的点 —— **同一条路只画一条线**，不再出现「同路两条线」的杂乱感；坐船/失败/假几何腿一律浅色虚线。

实测（杭州 3 天，起点西湖）：D1 = 湖滨步行街 → 河坊街 → 南宋御街 → 苏堤春晓 → 三潭印月（与竞品同方向，单线无重复路段）。
